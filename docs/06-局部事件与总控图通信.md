# 06 · 局部事件与关卡总控图的通信

> 对应需求文档 §19 第 7 项、§5.4。

---

## 1. 通信矩阵

| 发起方 | 目标 | 手段 | 是否等待 | 典型场景 |
| --- | --- | --- | --- | --- |
| 局部事件 | 状态 | `StateStore.set(key, value)` | 否 | `School.Story.DiaryFound = true` |
| 局部事件 | 总控图 | 完成通知（自动） | 否 | 事件正常结束 → 图节点 `done` 口传播 |
| 局部事件 | 总控图 | `RPGEventStudio.notify_graph(graph_id, node_id, payload)` | 可选 | 主动"报告进度"，如"已调查 2/3" |
| 总控图 | 局部事件 | `event` 节点 → `EventRunner.call_event(ref)` | 可配 | 播放演出并等它结束 |
| 总控图 | 公共事件 | `common_event` 节点 / `action` 内调用 | 可配 | 通用开门 |
| 总控图 | 状态 | `action` 节点批量写 | 否（事务内） | 进入追逐阶段：怪物巡逻 ON、关闭通路 |
| 总控图 | 场景对象 | `action` → `ObjectAdapter` | 否 | 启用/禁用节点、切 BGM、换环境 |
| 游戏脚本 | 两者 | `RPGEventStudio` 公开 API | 可配 | 玩家死亡 → 调公共事件 |

**核心约束**：局部事件与总控图**互不直接引用对方类**，只依赖中间层（`StateStore` + `EventBus` + `EventRunner` API）。这样局部事件不需要知道图的存在，图也不需要知道事件内部实现。

## 2. EventBus 信号表

```
signal event_started(ref: EventRef, instance_id: int)
signal event_finished(report: CompletionReport)        # COMPLETED / CANCELLED / FAILED
signal state_batch_committed(keys: PackedStringArray, revision: int)
signal stage_changed(level_id: StringName, from: StringName, to: StringName)
signal graph_node_activated(graph_id: StringName, node_id: StringName, cause: Dictionary)
signal graph_finished(graph_id: StringName, result: int)
signal custom_signal(signal_name: StringName, payload: Dictionary)   # 事件/图自定义信号
```

- 全部走同一个总线，**不做点对点 connect**（除了 runner 内部）。
- `custom_signal` 是需求 §3.3"游戏信号触发"的落点：游戏代码 emit，事件页 `trigger.type = SIGNAL` 订阅过滤。
- 信号只做通知，**不做状态载体**：任何"靠信号计数来推断状态"的逻辑都算缺陷（见 §5）。

## 3. 事件寻址（EventRef）

```
EventRef {
  kind: SCENE | RESOURCE,     # 场景内节点上挂的事件 / 独立资源事件
  uid: String,                 # .tres 的 uid:// 或场景的 uid://
  path: String,                # 场景路径（kind=SCENE 时）
  event_id: StringName,        # 场景内唯一 id
  cached_label: String         # 仅显示，失效时仍可读
}
```

- 运行时通过 `EventRegistry` 解析：`uid → 已加载资源`；`kind=SCENE` 时 `uid` 指场景资源，运行时在场景树里按 `event_id` 找到挂载节点（`EventInteractor2D` 在 `_ready` 注册自己）。
- 同一场景被实例化多份（两个教室）→ `event_id` 相同会冲突。规则：**场景实例化的多份共享同一事件定义**（参数可按实例覆盖，见下），不视为冲突。

### 3.1 实例级覆盖（可选，第二阶段）

```
EventDefinition 是被多个节点共享的模板
  → 节点上 `EventInteractor2D.event_overrides: Dictionary`（键路径 → 值）
  → 运行时合并：definition.params ⊕ overrides
```

这解决"两个宝箱共用一套事件逻辑，但给的物品不同"。第一阶段先不做，但数据模型保留字段。

## 4. 调用协议

### 4.1 图调事件

```
await RPGEventStudio.events.call(event_ref, args) -> Result
```

- `wait = false` 时立即返回，事件在后台跑；图节点收到 `done` 立即传播（不等待）。
- `on_fail`：`COMPLETE_ANYWAY`（默认）/ `ABORT_GRAPH` / `ERROR_PORT`。
- 事件内可读 `ctx.args`（图节点参数映射）与 `ctx.locals`。

### 4.2 事件调图

```
RPGEventStudio.graphs.notify(graph_id, node_id, payload)
RPGEventStudio.graphs.call_node(graph_id, node_id, payload) -> await Result
RPGEventStudio.graphs.request_stage(level_id, stage_id)      # 推荐写法：只改状态，由图监听
```

- `request_stage` 是"请求"，真正切换由 `StateStore` 的 `Stage` 写 + 图监听完成；事件不直接改 `stage` 的图状态。
- `notify` / `call_node` 是逃生口，用于"图里没有对应条件，但事件需要主动触发"的场景；过度使用说明图设计有问题，编辑器给出提示。

### 4.3 双向等待的边界

- 图等事件：`event` 节点 `wait = true`。
- 事件等图：**不推荐**。事件应写成"发请求 → 发完继续"，或者用 `wait_signal` 等图完成信号。
- 原因：事件等图会让调用栈变成环（A 等 B，B 又调 A），`max_call_depth` 会拦，但设计上就该避免。校验器对"图调用链 + 事件调用链"做环检测。

## 5. 状态为准，信号为通知（最重要的一条）

需求文档里的例子：

```
[调查办公室] → [获得教师日志] → [School.Story.DiaryFound = true]
                                      │
                              [通知关卡总控图]
DiaryFound == true AND ClassroomClueFound == true → [解锁地下室]
```

如果图依赖"收到通知"来推进，那么：

- 玩家先调查办公室（通知到达，条件 false）→ 图不推进；
- 玩家再调查教室（通知到达，条件 true）→ 推进 ✅

看起来没问题，但一旦出现：

- 读档后状态为 true 但没有任何通知 → 永远不解锁 ❌
- 两件事同帧完成 → 通知合并/丢失 → 少推进一次 ❌
- 图被禁用后重新启用 → 错过通知 ❌

**所以正确模型**：

1. 事件只写状态（必要时 emit 通知，但图**不依赖**通知内容）。
2. 图节点（`condition(monitor=true)`、`merge_and`）用**状态求值**判定是否推进。
3. 通知的唯一作用是"叫醒图去重新求值"，叫醒丢失最多导致延迟一帧，不会导致状态错误。
4. 读档、重进关卡、图中途启用 → 主动全量求值一次（`GraphRunner.refresh_all()`）。

这条规则决定了整个通信层的形状，也是评审时最容易被忽略、后期最难改的地方。

## 6. 完成语义

| 结果 | 触发 | 图节点默认行为 | 存档 |
| --- | --- | --- | --- |
| `COMPLETED` | 指令执行到结尾 / `结束事件` | 走 `done` | 记录 `completed` |
| `CANCELLED` | 调用方取消、场景切换、用户打断、被更高优先级中断 | 不传播，节点回 `WAITING`（可重试） | 不记录完成 |
| `FAILED` | 指令报错、参数非法、递归超限、资源缺失 | 按 `on_fail` 配置 | 记录失败原因（便于复现） |

"事件完成"在数据里是 `EventState.completed_count` + `last_result`，不是单个 bool——需要"可以重复触发的演出（每次进入都演）"和"只演一次"两种语义，用 `repeat_policy` 区分，用计数支撑统计与调试。

## 7. 去重与并发

| 场景 | 处理 |
| --- | --- |
| 玩家连点交互键 | 交互组件取按下沿 + 运行中实例表查重 + `repeat_policy` |
| 图与玩家同时触发同一事件 | `EventRunner` 全局实例表：同 `EventRef` 且 `reentry=DROP` 时第二次直接返回 `CANCELLED(busy)` |
| 并行事件与演出冲突 | 演出类事件默认 `priority` 高，并行事件在演出期间被推迟（`suspend_parallel_during_cinematic` 可配） |
| 图节点重复激活同一事件 | 节点 `reentry=QUEUE`，队列上限 8，超出丢弃并告警 |

## 8. 一次完整的跨系统流程

```
[玩家调查办公室桌子]
  EventInteractor2D → EventRunner.call(office_desk)
    CmdShowText("一页泛黄的日志…")
    CmdSetState Global.Story.DiaryFound = true
    CmdCallCommon("quest_toast", {text: "获得教师日志"})
    → COMPLETED
      → EventBus.event_finished
        → GraphRunner（订阅者）: 标记 monitor 的 condition 节点待求值
        → StateStore 批量提交 revision++
          → condition(ALL: DiaryFound && ClueFound) 求值 = false，不传播
[玩家调查教室]
  同上 → ClassroomClueFound = true
    → condition 求值 = true → 传播
      → action: School.BasementUnlocked = true
      → action: 播放"远处开门"音效、解锁地下室门对象
      → stage: 进入 basement_investigation（写 Level.Stage）
        → on_enter 指令：切换 BGM、镜头微震
        → 图高亮（编辑器内可见）
```

整条链路里没有一个事件知道"图"的存在，图也不知道"日志"存在，它们只共享状态 key 与事件引用。
