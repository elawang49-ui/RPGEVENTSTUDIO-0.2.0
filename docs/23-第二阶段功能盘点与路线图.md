## 2. 盘点结论

- 三项上一阶段任务（2/4/5 的基础部分）真实完成，测试与真机验收齐全；本阶段不重复建设。
- 最大缺口集中在 **创作期可视化审计**、**运行时可观测性**、**数据表达力（OR/多语言）** 与 **工程化（导出/压力）**。
- 输入系统有一条独立分支已实现增强能力，应优先整合而不是重写。
- `core/adapters/` 为空、没有导出配置、没有初始化向导：三者都属于“工程可用性”而非单点功能。

## 6. 建议实施顺序

1. **审计器**（本任务）：补上“看得见的问题”，后续所有任务的回归都受益。
2. **输入增强整合**：已有实现，先合入，避免后续任务在旧输入层上返工。
3. **运行时追踪**：与现有 debugger/F2 合并；为传送、压力测试提供观测手段。
4. **条件 OR**：数据表达力升级，牵动编辑器/运行时/扫描器，单独一轮。
5. **跨地图传送**：依赖追踪与场景生命周期，放在运行时稳定之后。
6. 其余 P2 按创作痛点排序：高级文案 → 自定义模板 → 触发形状 → 物品接口 → 向导/压力/导出。
7. 多语言放最后：需要单独设计增量 schema，不能动旧 `.tres`。

## 7. 本轮选择

选择 **全工程剧情资源审计器**：

- 依赖都是已完成模块，不需要改运行时；
- 与现有分支冲突面小（新增 core/editor 文件 + `plugin.gd`/`ui.csv`/测试注册）；
- 不改任何资源序列化格式；
- 创作者可以直接用，且后续追踪/压力测试可复用它的问题模型与定位能力。
