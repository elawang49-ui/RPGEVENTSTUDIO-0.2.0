---

## 1. 优先级定义

| 级别 | 含义 | 判断标准 |
| --- | --- | --- |
| P0 | 没有它就不是这个产品 | 事件执行、状态、事件页、交互触发 |
| P1 | 第一阶段之后必须尽快有 | 总控图、演出指令、多事件页、公共事件 |
| P2 | 有了体验完整 | 依赖分析、调试面板、路径编辑、存档 |
| P3 | 锦上添花 / 风险高 | 时间轴、AI、导入导出 |
| ❌ | 明确不做 | 通用可视化编程、背包/战斗/AI 系统 |

## 3. 六阶段路线（与需求 §17 对齐）

| 阶段 | 内容 | 验收 | 相对工期 |
| --- | --- | --- | --- |
| 1 | 最小可运行事件系统 | 钥匙 NPC 两段台词，零脚本 | 2 周 |
| 2 | 总控图原型 | 调查两处 → 自动解锁地下室 | 2 周 |
| 3 | 演出系统 | 进地下室自动演出 → 进追逐阶段 | 1.5 周 |
| 4 | 完整事件管理 | 多页、公共事件、自动/并行、依赖查询、存档、调试 | 2.5 周 |
| 5 | 高级编辑 | 对象选择器、移动路径、局部逻辑图、图调试高亮、调用关系 | 2.5 周 |
| 6 | 可选扩展 | 时间轴 / AI / 导入导出 / 静态检查 / 性能 | 视取舍 |

## 4. 明确延后及理由

| 延后项 | 理由 | 前置条件 |
| --- | --- | --- |
| 时间轴编辑器 | 事件指令列表已能完成需求 §7 的例子；时间轴会引入第二套数据模型与第二条执行路径，风险高收益低 | 事件指令列表在多角色同步场景被验证不够用 |
| AI 生成 | 架构只需预留 schema + JSON，不必先做 | 指令注册表稳定（第二阶段结束） |
| 任意指令中途精确存档 | 等于重放/回滚系统 | 演出采用"检查点 + 重播"已能满足剧情游戏 |
| 局部逻辑图（§8） | 与总控图共用 GraphEdit 与执行器，可低成本后置 | 总控图完成 |
| 完整撤销重做历史持久化 | 用户感知弱 | 无 |
| 状态引用索引的实时增量 | 全量构建 < 200ms（千级事件）已够用 | 工程规模超 2000 事件 |

---

## 5. 建议的下一步（按投入产出比排序）

1. **第一阶段 M0–M1**（骨架 + 数据模型）：一切的基础，返工成本最低。
2. **M2–M3 并行**（编辑器 + 运行时）：两边用同一份数据模型，能尽早暴露 schema 缺陷。
3. **M4 验收场景**：把"能不能用"变成可判断的事实。
4. 第二阶段总控图：先做 6 种节点（start/stage/condition/event/action/merge_and），够跑"解锁地下室"验收，再扩。
