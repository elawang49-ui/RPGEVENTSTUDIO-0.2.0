# 01 · 可行性评估与架构冲突

> 对应需求文档 §19 第 1、2 项。本文所有 API 结论均在 **Godot 4.7.2.stable.official（ed1daf0bf）** 上核实（`--doctool` 导出 1076 个类的 XML 逐一比对签名）。

---

## 1. 结论

**可行。** 需求文档要求的三个子系统（RPG Maker 式事件编辑器、关卡总控图、剧情演出）在 Godot 4.7 上都有对应的原生能力，且不需要第三方插件：

- 编辑器内嵌 UI：`EditorPlugin` + `EditorDock`（4.7 新停靠系统）+ 主编辑屏；
- 节点连线图：`GraphEdit` / `GraphNode` / `GraphFrame`（4.7 新增分组框类）；
- 撤销重做：`EditorUndoRedoManager` 支持 `custom_context`，可给"事件资源 / 关卡图资源"开独立撤销栈；
- 稳定引用：`ResourceUID`（`uid://`），资源重命名/移动不断链；
- 运行时注入：`add_autoload_singleton`。

真正的工作量不在"能不能做"，而在**三件事**：状态与数据模型的一致性（第 2、3 节）、编辑器的可用性（第 7、8 节对应文档）、运行时的可靠性（取消、重入、死循环）。

**最大风险不是技术能力，是范围失控**——需求里"可视化编程""时间轴""AI 生成""反向依赖分析"任意一项做深都会吃掉整个项目。第 9、10 号文档给出了硬性收口。

## 2. 已核实的 API 事实（4.7.2）

| 能力 | 4.7 实际接口 | 对设计的影响 |
| --- | --- | --- |
| 停靠面板 | `EditorPlugin.add_dock(dock: EditorDock)`；`EditorDock` 具备 `title`、`dock_icon`、`default_slot`、`closable`、`layout_key`、`available_layouts`（`DOCK_LAYOUT_VERTICAL/HORIZONTAL/FLOATING`）；`EditorDock.DockSlot` 含 `BOTTOM_L`/`BOTTOM_R`（比旧 `EditorPlugin.DockSlot` 多两个） | 事件指令列表、状态监视器、执行日志可各占一个可折叠/可浮动的 dock，用户可自由布局 |
| 旧式停靠 | `add_control_to_dock(slot, control, shortcut)` 仍存在 | 兼容路径，不优先使用 |
| 主编辑屏 | `_has_main_screen()` / `_make_visible()` / `get_plugin_name()` / `_get_plugin_icon()` | 总控图编辑器做成独立主屏（与 2D/3D/Script 并列），适合大图 |
| Autoload | `add_autoload_singleton(name, path)` / `remove_autoload_singleton(name)` | 运行时宿主注入；**必须成对清理**，见 §4-C |
| 撤销栈 | `EditorUndoRedoManager.create_action(name, merge_mode, custom_context, backward_undo_ops, mark_unsaved)` + `commit_action(execute)`；`get_object_history_id(obj)`；`EditorInterface.get_editor_undo_redo()` | 事件资源编辑、图结构编辑各用 `custom_context` 独立历史，不污染场景撤销 |
| 图容器 | `GraphEdit.connections: Dictionary[]`（getter `get_connection_list()`）；`connect_node(from_node, from_port, to_node, to_port, keep_alive)`；`get_connection_list_from_node(node)`；`get_connection_count(from_node, from_port)`；信号 `connection_request` / `disconnection_request` / `delete_nodes_request(nodes)` / `node_selected` / `begin_node_move` / `end_node_move` / `graph_elements_linked_to_frame_request` / `frame_rect_changed` | 4.7 把连接暴露成属性，但**写入仍应走 `connect_node`/`disconnect_node`**，不要直接赋字典数组（旧教程写法） |
| 图节点 | `GraphNode.set_slot(...)` / `clear_slot()` / `get_titlebar_hbox()` / `ignore_invalid_connection_type` / 槽颜色与类型 | 节点标题栏可放状态灯（运行中/已完成/条件不满足）；端口类型可用颜色区分 exec / cond |
| 分组框 | `GraphFrame`（`title`、`tint_color`、`autoshrink_enabled`）+ `attach_graph_element_to_frame` | 关卡"幕/阶段"分组直接落地 |
| 资源 UID | `ResourceUID.path_to_uid` / `get_id_path` / `ensure_path` / `create_id_for_path` / `id_to_text` | 事件、图、状态定义互引用一律存 `uid://`，路径仅作 fallback |
| 编辑器服务 | `EditorInterface.get_editor_undo_redo()` / `get_selection()` / `inspect_object(obj, for_property, inspector_only)` / `play_custom_scene()` / `get_editor_toaster()` / `get_command_palette()` | 定位对象、运行演示场景、非阻塞提示、命令面板（Ctrl+Shift+P）集成 |
| 图类型可用范围 | `GraphEdit` 官方标记为 `api_type="core"`（导出模板中也可用） | 但**设计上仍禁止运行时依赖 GraphEdit**，见 §4-C |

## 3. 六类真实约束（不是能力问题，是模型问题）

### 3.1 编辑器进程 ≠ 游戏进程

`EditorPlugin` 运行在编辑器进程里，活动场景处于"编辑态"：节点可被撤销、脚本处于 `@tool` 语义、没有 `_process` 游戏循环语义。

**结论**：事件**预览**必须在隔离环境跑——复制一份运行数据、用 Mock 宿主（无渲染、无真实节点），只验证指令流与状态变化；真实演出必须用 `play_custom_scene()` 起游戏进程。二者共享同一个 `EventRunner`，只是 `EventContext` 的实现不同。

### 3.2 上帝对象

"事件对象、事件页、触发器、状态、图节点"如果都写进一个 `EventController.gd`，三个月后必死。

**结论**：`core/` 里没有 `Node`，只有 `RefCounted` + `Resource`；节点侧只有薄组件（`EventInteractor2D` 约 100 行），负责"把场景事件翻译成运行时请求"。

### 3.3 RPG Maker 的"事件页"在 Godot 里没有天然容器

RPG Maker 的事件页挂在 Map 的 event 表上；Godot 里事件对象是场景节点，复制节点、实例化场景都会让"事件 ID"重复。

**结论**：`EventDefinition` 是**资源**，节点只持有引用；`event_id` 在**场景内**唯一，复制节点时由插件检测并重新分配；关卡图与存档只认 `uid://`，不认节点路径。

### 3.4 数据是 Resource，但编辑是"文档"

`Resource` 没有原生的"未保存/脏/多文档"概念，`ResourceSaver.save()` 是同步写盘。

**结论**：自定义 `EventDocument`（内存中的编辑会话，含脏标记、检查点、撤销上下文），保存时才写 `.tres`。所有写操作走 `Command`，命令负责同时更新数据、发信号、登记 undo。

### 3.5 中文界面与插件分发

插件要给别人用，界面全中文，但又不能让代码里散落中文字符串。

**结论**：源码字符串 + `tr()` + CSV 翻译表（`zh_CN` 为源语言，`en` 预留）。第一阶段只做中文，但**从第一天就 `tr()`**，避免后期全量替换。

### 3.6 性能不是"以后优化"

`GraphEdit` 节点超过 ~150 个、每节点内嵌多个 `OptionButton` 时，拖动会明显掉帧；事件页指令列表 500+ 行时，`ItemList` 重建一次就是几十毫秒。

**结论**：`GraphEdit` 节点采用"轻量外壳 + 懒加载参数控件"（缩放 < 0.55 或节点数 > 120 时切换为纯绘制模式）；指令列表用虚拟滚动（只实例化可视区 ±20 行）。这两条是**架构约束**，不是优化项，见 `docs/07`。

## 4. 架构冲突清单

| # | 冲突 | 具体表现 | 决策 | 代价 |
| --- | --- | --- | --- | --- |
| A | "NPC/机关零脚本" vs Godot 组件模型 | 需求说尽量不为每个 NPC 写 GDScript；但 Godot 里节点行为必须挂脚本 | 插件提供**通用组件**：`EventInteractor2D`（按键交互）、`EventTriggerArea2D`（进入/离开）、`EventAutoRun2D`（自动/并行）。用户只配置参数，不写代码 | 用户需理解"给节点加组件"这一 Godot 常识；文档要配图 |
| B | "统一状态服务" vs 编辑器/运行时双身份 | 编辑器里改状态不能影响真实游戏；但两边要用同一套 API | `StateStore` 是纯 `RefCounted` 数据层；编辑器持 `EditorStateStore`（含诊断与预览覆盖），运行时持 Autoload 内的 `StateStore`。**同一份代码，两个实例** | 必须严格禁止"编辑器实例写存档" |
| C | "总控图直接驱动游戏" vs "GraphEdit 只是个图" | 若执行器读 `GraphEdit` 节点树，运行时就绑死了编辑器 UI | 图数据 `LevelGraph` 是 `Resource`；执行器 `GraphRunner` 只读数据 + `GraphRuntimeState`；`GraphEdit` 仅是视图，且只在编辑器创建 | 视图与数据要同步，需要 `GraphViewAdapter`（约 300 行） |
| D | "事件页条件最大编号优先" vs 可视化拖动排序 | 用户拖动排序后"编号"含义变化 | **页序号 = 数据数组下标**；判定永远取"下标最大且条件满足"的页；拖动即重排数组，顺序即语义 | 用户需理解"越靠右优先级越高"，UI 上明示 |
| E | "事件列表 ↔ 节点图双向转换" | 需求明确**不要求**自动互转 | 不做。只做单向调用：事件指令可调图、图可调事件。绝不写 AST 转换器 | 复杂逻辑要用户在两种表示里二选一，需文档指引 |
| F | "尽量少侵入项目" vs 必须注入 Autoload | 运行时需要单例 | 只注入 **1 个** autoload（`RPGEventStudio`）+ 可选输入动作；不改场景根、不改玩家脚本、不接管 `_input` | 玩家控制由组件通过 `player` 组约定获取 |
| G | 事件对象身份 vs 场景实例化 | 复制节点/实例化场景导致 `event_id` 冲突 | `event_id` 场景内唯一；复制时校验器告警并一键重分配；图与存档用 `uid://` | 需要"事件清单"作为权威注册表 |
| H | 存档 vs 演出中途 | 任意指令中途精确恢复等于重放系统 | 检查点粒度 = **指令边界**；保存时若正在执行，回到上一个边界；复杂演出可配置"回滚到事件开头" | 玩家可能重看一段演出（可接受） |
| I | 中文 UI vs 插件国际化 | 硬编码中文不可维护 | `tr()` + CSV，源语言 zh_CN | 每次加 UI 多一步翻译表登记 |
| J | 4.7 新 Dock API vs 旧教程 | 网上大量 `add_control_to_dock` 示例 | 用 `add_dock(EditorDock)`，旧 API 仅作降级路径（若需兼容 < 4.7） | 需在 `docs/11` 决定最低支持版本 |

## 5. 明确不做（防过度设计）

对照需求文档，以下**不实现**或**只留接口**：

1. ❌ 通用可视化编程语言（无变量作用域、无函数、无自定义节点编译）。
2. ❌ 完整背包 / 战斗 / 敌人 AI（只提供 `ItemAdapter`、`QuestAdapter`、`EnemyAdapter` 三个接口）。
3. ❌ 视觉小说编辑器（只有基础对话框：文字、选项、头像、名字）。
4. ❌ 事件列表与节点图自动互转。
5. ❌ AI 直接生成可执行代码（只生成**结构化事件数据**并走校验器）。
6. ⏳ 演出时间轴（第六阶段，且只在事件列表满足不了多角色同步时才做）。
7. ⏳ 任意指令中途精确存档。
