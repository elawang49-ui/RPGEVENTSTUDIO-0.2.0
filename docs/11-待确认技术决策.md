## 🔴 D1. 事件对象怎么挂到场景里？

**背景**：需求要"尽量不为每个 NPC 写脚本"，但 Godot 里行为必须依附脚本。

| 选项 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 组件节点（建议） | `EventInteractor2D` / `EventTriggerArea2D` 等，挂在 NPC 下，配置 `event_ref` | 组合灵活、不侵入既有节点、可混用 | 每个事件对象多一个子节点 |
| B. 继承基类 | `class_name EventNpc extends CharacterBody2D` | 节点少 | 玩家已有基类时无法继承（Godot 单继承）→ 死路 |
| C. 场景元数据 | 用节点 metadata 存事件引用，运行时扫描 | 零节点 | 不可视化、易漏、无类型 |

**建议：A**。B 在真实项目里会被玩家控制器类冲突卡死；C 只作辅助（给"隐藏事件"这类无实体对象用）。
**影响**：`core/adapters` 与 4 个组件脚本；编辑器需要"一键给选中节点加事件组件"的菜单项。

---

## 🔴 D2. 数据存 `.tres` 还是 JSON？

| 选项 | 说明 |
| --- | --- |
| A. 纯 `.tres` | 类型安全、`uid://`、Inspector 可用；diff 噪音大 |
| B. 纯 JSON | diff 干净、AI 友好；无类型、Godot 无原生编辑 |
| C. 混合（建议） | 结构与引用用 `.tres`，指令参数用 `Dictionary`，JSON 仅作导入导出 |

**建议：C**（详见 `02` §4）。
**影响**：`core/model` 的序列化方式、`tools/` 的导入导出、校验器实现。

---

## 🔴 D3. 编辑器主界面放在哪？

| 选项 | 说明 |
| --- | --- |
| A. 独立主屏 "Event Studio"（建议）+ 停靠面板 | 大图编辑舒服；多占用一个主屏按钮 |
| B. 只做停靠面板 | 不占主屏；总控图在小面板里难用 |
| C. 独立窗口（`EditorDock` 浮动 / `Window`） | 可多屏；与编辑器布局管理耦合，易出 bug |

**建议：A**（第二阶段启用主屏，第一阶段只做停靠面板）。
**影响**：`editor/plugin` 注册方式、`docs/08` 的布局。

---

## 🔴 D4. 最低支持的 Godot 版本？

**背景**：本机是 **4.7.2**。`EditorDock` 与 `GraphEdit` 的属性化连接是较新 API；4.4/4.5 差异明显（旧 `add_control_to_dock`、`get_connection_list()` 为纯方法）。

| 选项 | 说明 |
| --- | --- |
| A. 只支持 4.7+（建议） | 代码最简单，可用最新 dock 与图 API |
| B. 4.5+ | 需要兼容层（dock、GraphEdit 连接读取） |
| C. 4.4+ | 兼容成本显著上升，收益低 |

**建议：A**，并在 `plugin.cfg` 里声明版本；若你的团队还在 4.5，改成 B（多约 1–2 天兼容层）。

---

## 🟡 D5. 交互键与玩家控制如何接入？

**背景**：插件不能假设玩家节点叫什么、用什么控制器。

| 选项 | 说明 |
| --- | --- |
| A. 约定 + 组（建议） | 玩家节点加入 `player` 组；插件创建 `rpg_event_studio_interact` 动作（可改键）；"禁止操作"通过 `PlayerAdapter`（默认实现：`set_physics_process(false)` + 清速度） |
| B. 完全由项目实现接口 | 灵活但每项目都要写适配代码，违背"少写脚本" |
| C. 接管 `Input` | 侵入性最强，冲突多 |

**建议：A**，`PlayerAdapter` 可被项目覆盖（继承 + 注册）。
**影响**：`core/adapters/player_adapter.gd` 与组件脚本。

---

## 🟡 D6. 状态 key 的命名与作用域判定

| 选项 | 说明 |
| --- | --- |
| A. 点分字符串 + `StateDefinition.scope`（建议） | 可读；作用域在定义里，不在字符串里猜 |
| B. 结构化 key（`{scope, level, path}`） | 类型安全；编辑器输入繁琐 |

**建议：A**，但 Level 作用域的 key 必须带关卡前缀（`School.Stage`），`@@self` 仅事件内有效。
**影响**：`StateKey` 解析、校验器、选择器。

---

## 🟡 D7. "事件完成"的语义

| 选项 | 说明 |
| --- | --- |
| A. 三态（完成/取消/失败）+ 完成次数（建议） | 演出可重播、失败可诊断；数据多一个字段 |
| B. 布尔 `done` | 简单；无法表达"取消"与"重播" |

**建议：A**（`docs/04` §11）。
**影响**：`CompletionReport`、图节点 `on_fail`、存档结构。

---

## 🟡 D8. 关卡阶段是"状态"还是"图节点"

| 选项 | 说明 |
| --- | --- |
| A. 状态为准，图节点是镜像（建议） | 单一真相；存档只存一个 ENUM |
| B. 图节点持有阶段 | 图形直观；易与状态分裂 |

**建议：A**（`docs/03` §5）。
**影响**：`StageWatcher`、图高亮、存档。

---

## 🟡 D9. 存档由谁负责？

| 选项 | 说明 |
| --- | --- |
| A. 插件提供 `SaveService` + 插件自有存档文件（建议） | 开箱即用；与项目自有存档并存需合并 |
| B. 只提供快照 API，项目自己存 | 灵活；每个项目要写代码 |
| C. A + B（默认实现可替换） | 最稳，多一点工作量 |

**建议：C**（默认 `user://rpg_event_studio_save.dat`，可注入 `snapshot()/restore()` 到项目存档）。
**影响**：`core/save`。

## 🟡 D10. 中文界面与国际化

| 选项 | 说明 |
| --- | --- |
| A. 源码中文 + `tr()` + CSV（建议） | 现在只出中文，将来可加英文 |

**建议：A**。

## 🟡 D11. 事件与节点绑定的"身份"策略

| 选项 | 说明 |
| --- | --- |
| A. `event_id` 场景内唯一 + 复制时重分配（建议） | 简单直观 |
| B. 场景内 `NodePath` 为身份 | 改名即断 |
| C. 每个事件对象一个独立 `.tres` 资源（1:1） | 复用差；但引用最稳 |

**建议：A**，`NodeRef` 多字段兜底（`docs/02` §5）。
**影响**：`EventRegistry`、校验器、复制节点逻辑。

## 🟡 D12. 第一阶段是否包含"公共事件"？

需求 §17 第一阶段没列公共事件，但验收场景里"给钥匙 + 提示"很自然会用到。

| 选项 | 说明 |
| --- | --- |
| A. 包含最小公共事件（无参数、串行调用）（建议） | 多约 0.5 天；避免第二阶段返工数据模型 |
| B. 完全不包含 | 快 0.5 天；数据模型仍留字段，第二阶段补 |

**建议：A**（只做无参数版本，参数化推到第二阶段）。
**影响**：`CommonEvent` 类、`call_common` 指令、递归防护。
