# 05 · 关卡总控图：数据结构与执行模型

> 对应需求文档 §19 第 6 项、§5。

---

## 1. 它与"流程图"的本质区别

| | 流程图 | 本项目的关卡总控图 |
| --- | --- | --- |
| 用途 | 画给人看 | 运行时直接驱动游戏 |
| 状态 | 无 | 每个节点有运行状态（未激活/等待/运行中/完成/失败） |
| 时序 | 一次性走完 | 长期驻留，随状态变化反复求值 |
| 并发 | 无 | 并行分支、AND 汇合、等待外部事件 |
| 重入 | 无 | 允许同一节点被多次激活（策略可配） |
| 与游戏关系 | 文档 | 唯一真相：阶段、开关、解锁条件都由它推进 |

**执行模型一句话**：图是一个**令牌流网络**，节点接收激活令牌并决定是否向下游传播；状态变化是最主要的外部激励源。

---

## 2. 数据模型

```
LevelGraph (Resource)
 ├─ graph_id, level_id, entry_node, schema_version, view_state
 ├─ nodes: Array[LevelNode]
 ├─ connections: Array[LevelConnection]
 ├─ groups: Array[GraphGroup]
 └─ stages: Array[StageDefinition]
```

**LevelNode**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `node_id` | `StringName` | 图内唯一，**与视图里的 GraphNode.name 一致**（便于高亮定位） |
| `type` | `StringName` | `start` / `stage` / `condition` / `event` / `common_event` / `action` / `merge_and` / `merge_or` / `parallel` / `wait_signal` / `end` / `subgraph` / `note` |
| `title` | `String` | 显示名，可覆盖（默认取 type 的本地化名 + 关键参数摘要） |
| `params` | `Dictionary` | 由节点类型定义（见 §3） |
| `position` | `Vector2` | 图坐标系 |
| `size` | `Vector2` | 用户手动尺寸，0 = 自动 |
| `reentry` | `int` | `DROP` / `QUEUE` / `RESTART` |
| `enabled` | `bool` | 禁用后其上游令牌到此为止（用于灰度/调试） |
| `comment` | `String` | 备注 |

**LevelConnection**

```
{ from_node: StringName, from_port: StringName, to_node: StringName, to_port: StringName, enabled: bool }
```

端口名而不是下标：`out` / `true` / `false` / `case:0..n` / `in`。用名字是为了**改端口顺序不破坏连线**。

**GraphGroup**：`{ id, title, color, node_ids, collapsed }`，对应 GraphFrame。

## 3. 节点类型

| 类型 | 端口 | 参数 | 语义 |
| --- | --- | --- | --- |
| `start` | out | 触发条件（关卡进入 / 手动） | 关卡开始，唯一入口；重复进入幂等 |
| `stage` | in, out | `stage_id`、`on_enter_commands`、`on_exit_commands` | 进入阶段：写 `Level.Stage` → 触发进入事件 → 传播 |
| `condition` | in, true, false | 条件树 | 求值并走 true/false；支持 `monitor` 模式（状态变化自动重求值） |
| `event` | in, done | `event_ref`、`wait`、`on_fail` | 调用局部事件，可等待完成 |
| `common_event` | in, done | `common_ref`、参数映射 | 同上 |
| `action` | in, out | 动作列表（设开关/改变量/启停对象/换 BGM/阶段切换） | 原子执行，立即完成 |
| `merge_and` | in×N, out | `required`（默认全部）、`timeout` | 等齐所有入边令牌 → 传播；超时走 `timeout` 口 |
| `merge_or` | in×N, out | — | 任一入边令牌 → 传播 |
| `parallel` | in, out×N | — | 同时向所有出边发令牌，后续各自独立 |
| `wait_signal` | in, out | `signal_name`、`filter` | 挂起直到 `EventBus` 收到匹配信号 |
| `end` | in | `completed_key`、`next_level` | 关卡完成：写 `Level.Completed`、解锁下一关 |
| `subgraph` | in, out | `graph_ref`、`input_map` | 子图（复用一段总控逻辑，如"通用开门流程"） |
| `note` | — | 文本 | 纯注释，不参与执行 |

**为什么没有"分支/汇合"两种通用节点**：`merge_and` / `merge_or` 已覆盖汇合；分支由 `condition`、`parallel`、以及 `event.done` 的多出边承担。节点类型越少，编辑器越不容易劝退。

---

## 4. 连接合法性

- 端口有类型：`exec`（主流程）、`bool`（true/false）、`done`。`GraphEdit.add_valid_connection_type` 用来限定，避免 exec 连到 bool。
- 校验规则：
  - `start` 无入边；`end` 无出边。
  - 非 `note` 节点必须至少一条入边（`start` 除外），否则 Linter 报"孤立节点"。
  - `merge_and` 的 `required` ≤ 入边数。
  - 禁止自环（`from == to`）；跨节点环由 `GraphLinter` 检测（见 §8）。
- 4.7 的 `GraphEdit` 用 `connect_node()`/`disconnect_node()` 写入；`connections` 属性只读来同步，**不要**直接赋值字典数组（旧教程写法在 4.7 语义下不可靠）。

## 5. 执行模型

### 5.1 令牌与激活

```
Activation { node_id, token_id, inputs: Dictionary[port -> value], cause: {kind, ref} }
```

- 外部激励产生根令牌：关卡进入、状态变化（监控节点）、事件完成信号、手动调用。
- 节点收到令牌 → 按类型决定：立即传播（action/parallel/stage）、求值后传播（condition）、挂起等待（event/wait_signal/merge_and）、完成（end）。
- 令牌**携带来源**（cause），用于日志与"为什么这个节点激活了"的反向追踪。

### 5.2 节点状态

```
UNVISITED → WAITING_INPUTS → RUNNING → DONE
                                └────→ FAILED
```

- `merge_and` 需要计数：每收到一条入边令牌，记 `(node_id, token_id) -> {received: {port -> true}, received_at}`；凑齐 `required` 后一次性 RUNNING。
- 令牌超时未凑齐 → 清空并记录"未汇合"诊断（常见于条件分支走错）。

### 5.3 重入策略

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| `DROP`（默认） | 运行中再来令牌 → 丢弃并计数 | 阶段节点、一次性解锁 |
| `QUEUE` | 排队，当前完成后依次处理 | 事件节点（防止连点触发两次演出） |
| `RESTART` | 中断当前，从头再来 | 追逐阶段的"重新开始"逻辑 |

运行中状态持久化在 `GraphRuntimeState`，存档一并保存（队列也保存，避免读档后丢令牌）。

### 5.4 传播与预算

- 同一帧内深度优先传播，**状态写入走 `StateStore.transaction()`**，整支传播结束才提交 → 避免每个 Action 触发全图重求值。
- 每帧传播预算：`graph_ops_budget = 64` 个节点/帧，超出排队。
- 防爆保护：单次传播最多 `max_hops = 512`，超出报"图传播疑似死循环"并中止本次传播。

### 5.5 求值触发源

1. `StateStore` 批量提交（监控中的 condition 节点重新求值）。
2. `event_finished` / `event_started`。
3. `wait_signal` 匹配的信号。
4. 手动：编辑器调试面板"运行此节点"、游戏内脚本 `RPGEventStudio.graphs.call(graph_id, node_id)`。
5. 关卡进入 / 场景就绪。

## 6. 运行时状态

```
GraphRuntimeState {
  graph_id
  node_states: { node_id: { state, last_enter_at, run_count, last_result } }
  pending: { token_id -> Activation }
  merge_buffers: { node_id -> { token_id -> {ports, first_at} } }
  queues: { node_id -> Array[Activation] }
  revision: int
}
```

- `GraphRunner` 每图一个实例，持 `LevelGraph`（数据）+ `GraphRuntimeState`（状态）。
- **视图只读 `GraphRuntimeState`**：编辑器高亮当前阶段、运行中节点就是订阅这里的信号。运行中的游戏把状态通过 `EditorDebuggerPlugin`（可选，第二阶段后）或调试端口推给编辑器；第一阶段只做"编辑器内 Mock 预览高亮"。

## 7. 条件节点的内部结构

`condition` 节点的 `params.condition` 是一棵条件树（与事件页共用 `ConditionNode`，见 `docs/04` §15）：

```
ANY
 ├─ LEAF School.Story.DiaryFound == true
 └─ ALL
     ├─ LEAF School.Story.ClassroomClueFound == true
     └─ NOT LEAF School.BasementUnlocked == true
```

- `monitor = true` 时：订阅条件里出现的所有 key，任一变化 → 重新求值；只有**求值结果翻转**才传播令牌（防止抖动）。
- 需求 §5.1 的"办公室/教室任意顺序调查，两者都完成才解锁地下室"就是：两个 `event` 节点 → 各自 `action` 写状态 → `merge_and`（或一个 `condition(ALL)`）→ 解锁节点。两种画法都合法，推荐 `merge_and`（更直观地表达"等两件事都完成"）。

## 8. 静态检查（GraphLinter）

| 检查 | 算法 | 输出 |
| --- | --- | --- |
| 不可达节点 | 从 `start` 沿 `out/true/false/done` 做 DFS，未访问者标记 | 警告 + 一键定位 |
| 环路 | Tarjan 强连通分量；含 `wait_signal`/`event` 的环视为合法等待环 | 错误（硬环）/ 提示（软环） |
| 悬空连接 | 连线端点不存在 / 端口不存在 | 错误 |
| 缺失条件 | `merge_and` 的 required 大于入边数；condition 无出边 | 警告 |
| 重复触发风险 | 同一节点有多条无条件路径且 `reentry == QUEUE` 无上限 | 提示 |
| 阶段完整性 | `stages` 里定义的阶段都有对应 `stage` 节点；`stage` 节点引用的阶段都存在 | 错误 |
| 死亡分支 | `false` 口无下游且无注释 | 提示 |

## 9. 反向追踪与依赖分析（需求 §5.5）

三层索引（由 `DependencyIndexer` 构建，编辑器打开工程时增量更新）：

1. **节点级**：`前置 = 所有上游节点（按 AND/OR 语义展开）+ 自身条件引用**
2. **状态级**：`writes[key]` / `reads[key]`（扫事件指令与图节点）
3. **事件级**：`calls[event_ref]`、`called_by[event_ref]`

查询 `explain(node_id)` 输出（对应需求文档的示例格式）：

```
第三幕：逃离学校
├── 前置条件
│   ├── 地下室剧情完成        [event basement_intro → COMPLETED]
│   └── 追逐阶段启动          [stage chase]
├── 关联对象
│   ├── 教学楼出口            [NodeRef → scenes/school/main.tscn :: Exit]
│   ├── 怪物 AI               [adapter:enemy → EnemyAdapter.set_active]
│   └── 逃生演出              [event escape_cutscene]
└── 完成后影响
    ├── School.Completed = true      [writes]
    └── 解锁下一关                    [end 节点 → next_level]
```

点击任一条目 → 定位（事件资源 / 图节点居中 / 2D 视口选中节点 / 状态面板过滤）。

## 10. 视图与数据同步（GraphViewAdapter）

```
LevelGraph（数据，唯一真相）
   │  ① build/refresh
   ▼
GraphEdit + LevelNodeView（视图）
   │  ② 用户交互 → 命令
   ▼
GraphEdit 信号：connection_request / disconnection_request / delete_nodes_request /
                end_node_move / graph_elements_linked_to_frame_request
   │  ③ Command（AddNodeCommand / ConnectCommand / MoveCommand…）
   ▼
EditorUndoRedoManager(custom_context = LevelGraph 资源)
   │  ④ 改数据 → emit changed
   ▼
① 增量刷新视图（只更新受影响的 GraphNode）
```

要点：

- **数据 → 视图单向重建，视图 → 数据单向命令**，不做双向绑定（否则撤销时互相触发）。
- 拖动节点：`end_node_move` 才提交一次 `MoveCommand`（合并同一节点的连续移动），避免 60 次/秒的撤销记录。
- 连接：`connection_request` 里先校验端口类型与规则 → 合法才 `connect_node` + 记命令。
- 删除：`delete_nodes_request(nodes)` 里连带的连线一并进同一条命令。
- 视图刷新时**屏蔽信号**（`_suppress_view_events = true`），否则会回灌命令。

## 11. 编辑器性能

| 手段 | 触发 | 效果 |
| --- | --- | --- |
| 轻量节点外壳 | 节点数 > 80 | 只保留标题 + 一行摘要，参数控件按需展开 |
| 简版绘制 | `zoom < 0.55` | 隐藏节点内子控件，用 `_draw` 画状态色块 |
| 分帧构建 | 打开图时 | 每帧最多建 12 个 GraphNode，进度条提示 |
| 懒求值高亮 | 运行调试时 | 只高亮可见区域（`get_connections_intersecting_with_rect` 可辅助） |
| 折叠分组 | 用户主动 | `GraphFrame` 收起成员，GraphEdit 原生支持 |

`view_state`（缩放/滚动/分组折叠）单独存 `.tres` 的 `view_state` 字段，不参与运行时，避免"改个滚动位置弄脏数据"。
